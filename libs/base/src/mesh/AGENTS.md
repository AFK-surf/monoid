# The mesh's device side (for agents)

Part of the base (`libs/base/AGENTS.md`): it knows no program.

## What a program on it gets with it

- A peer's bytes are kept up to the caller's bound: a whole reply (`Reply::rest`, `max_body`) and one event-stream block (`Sse::new`, `max_event`), 16 MiB each unless said, then failing (`too_long`, `TooLong`). Longer reads stream (`Reply::take`, a duplex's reply, `Inbound::take`), keeping none: a reader that stops holds the peer back by the transport window, and a told body (`Link::request`'s `wrote`) has at most one 64 KiB step waiting. An unread reply can be handed to the shell (`Reply::tap`, `istream.tap`) with what was read past its head; if the shell declines, it is read as ever.
- A connection a peer dials in (`Mesh::incoming`, only where `Binding.takes` names a protocol) is never a link: no credential, ping or `links` entry knows it. The mesh keeps one nobody took yet; its first line is held to `first_ms` (30 s) and 64 KiB (`Incoming::first`). Later streams, the peer's (`Incoming::accept`) and the program's (`Incoming::open`), are awaited in the mesh's fibers like a link's and are the program's to bound (how long, how many); while one is open the endpoint is not rebound.
- `Mesh::dial_once` dials a peer on a program's protocol: no link either, on an endpoint bound for it alone with a drawn key, never the device's (on the device's relay the same endpoint id would put that one off), so it proves nothing of the device; that is the program's to send (`Mesh::sign`). Connection and endpoint close as it closes, ends, fails, is given up or the mesh closes.
- `Mesh::connect` dials on the endpoint itself, so the peer's transport proves the device (no relay put off), and hands out an `Incoming` like a dialled-in one; it counts as on the endpoint while it lasts.
- A peer's hello answer's `lan` / `tailnet` addresses (IPv4 `a.b.c.d:port`, 8 each, as the TypeScript mesh checks) are kept by place in the program's `Store` (`Mesh::make`'s `addresses`), unreadable values taken as none. A dial given them does not wait to be on a relay (`onto_max_ms`). `iroh.addAddr` is an op answered at once (`Shell::ask`), never a call, in the Rust shell.
- The mesh passes `forget: true` on every last `conn.close` and `iroh.close`: both shells then drop the connection or endpoint whole with its streams.
- Ways (`ways.mbt`'s head): a place is dialled on the endpoint alone unless its endpoint's ways are `off`, direct is held for flakiness, its last dial with the same addresses went unanswered, or its link died of missed pings; then every way races. Numbers are the TypeScript mesh's: change both together. A relay endpoint's key is SHA-256 of `pinned_prefix`, device key and relay, so the TypeScript prefix gives its keys. On purpose unlike it: a missing endpoint way is redialled every `redial_main_ms` (dead code at `mesh.ts` `#steer`); `relay_only` does not turn endpoint ways off; LAN and tailnet endpoints get drawn keys. Only the endpoint's own dial says whether it is stuck or unanswered (`Mesh::dial_main_raced`); races and a wake's second dial use `Mesh::dial_all`.
- Speeds and days (`speed.mbt`) use the program's wall clock (`Mesh::make`'s `clock`, the runtime's UTC unless given), kept under their keys in its `Store`; a speed comes only from replies the program times (`Mesh::timed`) and weighs in `Score.cost`. The day's tally runs only while a link is open.
- Spans and records (`trace.mbt`) match the TypeScript mesh by name and attribute, but the peer's attribute is named by `Trace.peer_key` (`"peer"` by default): this library never says another program's word. Records are built only while `Recorder.on`; a place is observed (paths, `conn ways`, `dht`) once a tick, by the ways' fiber while steered, else by its link's.
- `Mesh::sign` asks the shell (`ed25519.sign`) and signs in `sign.mbt` only where it cannot (a page): TweetNaCl's code, not constant-time beyond that, signing only what it is given. Its check (`double_scalarmult`) is not constant-time at all (public bytes only): never sign with it. `Mesh::verify` asks the shell (`crypto.verify`), else `sign.mbt` `ed25519_verify`, which refuses what libcrux refuses (`S` past the order, a non-canonical point): change both together. `Mesh::migrate` rebinds on the given key and drops everything on the old one at once.
- The device key file is its user's alone whatever the umask, by the Rust shell only (`client/shell/src/lib.rs` `create_private`): a program linked to an older shell keeps its umask's. `shell.c` has run on macOS arm64 only (also compiled for Linux, glibc 2.28).

## Known, and left

What was known when the library moved here (2026-11-14) is mended, each with a test that failed before; what is left is another part's:

- Natively the Rust shell takes every connection dialled to an endpoint taking a protocol once `iroh.accept` is first asked, queueing unasked ones without bound (`client/shell/src/lib.rs`, `Accepted`); the mesh asks one at a time. The shell's to bound. A page's shell has no `iroh.accept` (`Mesh::incoming` fails there).
- A given-up write frees its stream (`Out::write` resets it), in both shells only once that write moves: `istream.write` holds the send half while writing and `istream.reset` waits for it (`client/shell/src/lib.rs`, `client/iroh-wasm/src/lib.rs`), so against a peer not reading, write and reset wait until it reads, stops or the connection ends. The shells' to mend, for the TypeScript device base too.
- A read waiting as its connection ends can get the stream's end from the Rust shell, not a failure; the mesh has no length of its own, so a cut reply passes as whole (`requests_wbtest.mbt` scripts it): a reply head's length is the program's to enforce until that shell answers a failure. As in the TypeScript device base.
- On js under Hermes, MoonBit's `Array` growth costs the square of its length (a full one is copied into `new Array(n)` from the end down: 40,000 pushes 0.6 s, 80,000 2.7 s, against 3 and 6 ms for native `push`; Hermes of React Native 0.81.4, 2026-11-14), and `StringBuilder` and `join` rebuild their string per piece. The event-stream reader keeps one event's lines out of both (`sse_js.mbt`); `Sse::feed` still returns an `Array`, so a chunk ending tens of thousands of events pays it, as does anything else that grows one. MoonBit core's to mend; no program runs this under Hermes.

## Fibers and shell lifetimes

- `catch` does not catch interruption: cleanup goes in `defer`. `Mesh::close` notifies pending openings, live links and waiting dialers before cutting fibers, so nothing hangs if cut before its first step.
- Only a dial can be cancelled in the shell (`Shell::give_up`). An interrupted stream read or write leaves the stream unusable, so it is reset (`Reply::cancel`, `Out::write`), and control-stream exchanges (`Mesh::ping`, `Mesh::race`) and stream opens/accepts (`open_on`, `accept_on`) run in the mesh's own fibers.
- `Mesh::rebind` rebinds only when `Mesh::idle` finds nothing active; callers never keep the endpoint handle across waits.
- `Mesh::retune` to other relays drops every link first, as `drop_link` does (peers told the caller's reason), then binds once their ends are told; never closes the endpoint under live links. A failed bind leaves links gone and old relays kept until a dial finds it idle. Entries alone (`iroh.setRelayEntries`) are told one at a time, never rebinding.
- The `iroh.accept` wait outlives an endpoint: it is dropped in the step the endpoint changes (`Mesh::forget_coming`), and fiber and asker check it is still the kept one before taking its answer.
- After every wait in `ways.mbt` the mesh, the place in `links` and the `pinned` entry are read anew; a dial's result is a way or closed in the step it comes (`Mesh::adopt_way`); `release_pinned` closes nothing while `dialing`. A ping not yet late is not counted again (`Mesh::remeasure` pings links their ticks ping too).
- Native device keys are `0600` (`create_private`); `shell.c` needs POSIX (`pthread`) and system randomness: `getrandom` on Linux (glibc >= 2.25, so a glibc 2.28 build links), `arc4random_buf` on Apple systems and the BSDs.
