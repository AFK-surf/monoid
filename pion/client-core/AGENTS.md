# Working in `pion/client-core` (for agents)

Pure-Pion client core workspace (`pion.toml`) on top of `pion/base` and official `AFK-surf/pion-packages` Git tags (`base64-v0.1.0`, `effect-v0.1.0`, `crypto-v0.4.1`, `flate-v0.1.0`, `url-v0.1.0`, `time-v0.1.0`, `http1-v0.1.0`, `json5-v0.1.0`, `markdown-v0.3.0`, `regex-v0.1.0`), designed for two goals at once:

1. Strongly typed, immutable internal domain structures, zero-write cold chat open, and zero-serialization `FrameOutbox[T]` ready to feed the Invar render thread directly.
2. A removable thin JSON protocol adapter (`packages/protocol`) and C ABI bridge (`packages/core_abi/native/core_pion.c`) implementing all 6 functions of `apps/mbui/src/host/core_api.h` so `apps/mbui` can mount it during transition without changing a line.

## Rules

- Opening a chat writes nothing before its first view is built (`open_chat` performs 0 SQL writes, preloads `md_kept` in 1 statement, and keeps statement count constant as account chat count scales 5×). Pending `log_use` / `md_kept` writes flush afterward in one `Burst` transaction via `MdStore::flush_turn`.
- Never scan `chat` whole; keep all list reads bounded by indexes (`chat_recent`, `chat_thread`, `chat_session`, PK).
- Keep `md_key`, `entry_min_rows`, and SQLite schema byte-compatible with `client/core-ts` and `libs/client-core`.
- Each data directory `<dir>` is owned exclusively by a single `core_runtime` instance at a time, enforced by `pion_core_dir_owner_lock_acquire` (recursive dir creation + `<dir>/.core.lock` via non-blocking `flock(LOCK_EX | LOCK_NB)` on POSIX and UTF-16 `CreateFileW` + `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)` on Windows). A second instance targeting the same `<dir>` fails fast (`data_dir_locked`) without touching any database or blocking the worker thread, and the OS kernel automatically releases the lock on `mb_core_stop()` or process exit/crash. Under exclusive directory ownership, `<dir>/accounts` is the sole persisted account source of truth, updated ONLY via unified 16 MiB-bounded atomic temp+`fsync`+`rename`+strict dir `fsync` (`pion_core_accounts_write_atomic`, 3-state `0`/`-1`/`-2` + `pion_core_accounts_sync_dir`) or zero-block `unlink` when empty (`pion_core_accounts_remove_atomic`), with a startup `pion_core_accounts_sync_dir` fence before reading `<dir>/accounts`, serialized in-process by per-session `AccountRefreshCoordinator`. Storage fault boundary (aligned 1:1 with TS `client/core-ts/src/accounts.ts:678-681`): when the underlying OS/filesystem refuses all writes to `<dir>` (e.g. `EROFS`/`EIO`/`chmod 0500`), the live process closes the read gate in 0ms and filters rejected tuples in memory across subsequent writes, while Cloud remains the ultimate authority on cold restart (first 401 closes the read gate immediately; no second non-atomic local lease/marker file is layered).
- Use qualified `crypto::sha256_hex` / `crypto::sha256` (avoid unqualified `sha256_hex` shadowing in `pionc 0.1.0`).
