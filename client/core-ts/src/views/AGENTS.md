# Client core locks, handover, and presets (for agents)

## A lock held here

- **Active chain and fork choice**: Write a workspace `lock` chain or personal pinned chain (`client/core-ts/src/personal-lock.ts`) only through `client/core-ts/src/views/lock.ts` `hold` and `personal-lock.ts` `#heard`/`#pin` using rules fork choice (`client/core-ts/src/lock-keep.ts`, forks kept up to `ASIDE_MOST`). Never append an entry whose `prev` does not match the head hash. Carry missing station-known entries to peers (`client/core-ts/src/views/lock.ts` `carry`).
- **Signing and retries**: Sign one entry at a time per lock (`Lock.append`, `#append`). Re-sign displaced entries only under `lock-keep.ts` `againOf` (up to `AGAIN_MOST` times, and for personal locks only when the seed is already in hand). Never silently drop a failed user entry: surface it as a failed pending entry (`#letBe`).
- **No background prompts for sealed secrets**: Background work (incoming lock updates, retries, background writers) must never read a presence-sealed secret or prompt the user. Only explicit user actions read a sealed secret once. Background rekeying waits until the key is next unsealed (`client/core-ts/src/views/vault.ts`).
- **Station acceptance vs. cloud**: Cloud acceptance never counts. Keep entries not yet accepted or refused by a named station in `client/core-ts/src/lock-pending.ts` (never on the chain), show them as pending, and deliver on station reads (`deliver`), never on a timer. Mirror an entry to cloud only after a station accepts it, except when a lock names no stations or a personal lock starts anew.
- **Automatic personal lock (`ownLockFor`)**: Safe-mode members receive a personal lock automatically (`client/core-ts/src/views/lock.ts` `ownLockFor`, `vouchersIn`): trusted workspace-lock devices put themselves on it via the device that approved them so nobody re-approves. Known accepted trade-off: before a member pins a lock, a modified-app owner or admin can voucher a device via workspace lock rewrites (the entries stay recorded). Do not widen this rule (never by device id, never the approver of a device already on the lock), and do not narrow it without owner approval.

### Moved workspaces (`moved {root}`)

- Compute effective state via `rules` (`state4_moved` in `client/core-ts/src/lock-moved.ts`, read through `client/core-ts/src/views/lock.ts` `stateOf`) from the moved chain, personal logs (`lockLogs`), and statement bodies (`lockBodies`, synced by head hashes via `GET /lock/heads` and `POST /lock/given`). Never sign on the moved chain (`Lock.append` returns `lock_moved`). Determine safe mode via `client/core-ts/src/views/lock.ts` `safeMode` (`lockSafe`), falling back to cloud `locked` only when no lock is held. Clear a station's `left` refusal when it admits the device (`readLockOnce`), and treat a `left` refusal on a cached `off` moved workspace as waiting for approval so re-enabling safe mode never strands an unlisted device.
- Express post-move workspace changes as statements in the actor's personal log (`client/core-ts/src/lock-statements.ts` `sayMoved`), prompting the person each time so an unlocked stolen phone cannot alter rosters or undo its removal. Simulate effects via `rules` first: re-state any collateral removals (removing one person must not remove others) and refuse no-op statements. Send bodies only to stations named in that workspace's list, never to cloud or another workspace's station.
- Only the root person disables or re-enables safe mode on their bound log (`lock_root_only`, naming them and `stillfail lock reset`). Turning a workspace off prompts once, for `off` (or `disable`) alone: no vault is opened or written out in plain text.
- Web sessions in a moved workspace require at least one app device on that person's log (`web` approved face to face, else return `lock_needs_app` / `needsAppIn`). Web-only members do not block a move and keep their session until `exp`.
- When admitting a newcomer (`member {sub, email, lock, role}`), use `notedRole` (defaulting to `member`) capped by the cloud view's role, never trusting cloud alone.
- Before removing a device or member, level vaults from reachable stations (`levelVaults`, `takeBefore`) verifying against the pre-removal state. Removal reads no box key. Rekeying vaults for removed members waits until the owner next unseals the key.
- User-facing errors: untrusted devices return `core-misc.lock.notSigner` (`notTrustedHere`), another member's device returns `core-misc.lock.othersDevice`. A device refused at a move boundary retries automatically on its link retry without asking the user to act.
- Restarting a personal lock (`lock.restartOwn`, 我的其它设备都不在了) or adopting one started elsewhere (`lock.forgetOwn`) requires an explicit user press, offered only after no device answered (`restartText`) or the lock was `replaced` (`forgetText`). While a workspace still binds the old lock, tell the person who can remove and re-add them (`reboundIn` via `left.apps`).
- A station that previously held the lock (`lockServes` `pinned`) and now holds none was reset (`stillfail lock reset`): never re-upload via `bringMoved`, only via an owner's 保护 (`stationMoved`). When all stations in the effective state hold no lock, drop local lock state and (unless the held chain is already disabled, where the `disable` entry is being mirrored to the cloud) delete the cloud copy (matching `lock_exists` on re-enable).

### Seamless handover (`handOver`, 无感迁移)

- `handOver` (`client/core-ts/src/lock-handover.ts`, `client/core-ts/src/views/lock.ts`) runs automatically after `HAND_OVER_FROM` once all named stations advertise `bodies`, `logs`, `builds`, `carried`, `bind` (plus `heads` above `LOGS_BEFORE` logs) and this device meets `MOVED_FROM_BUILD` (`LOGS_ANY_FROM_BUILD` for large workspaces). It writes nothing to personal logs and prompts nobody. `lock.handOver` returns `unknown_call` unless automatic or `handOverByTests` is set on the host. Never re-sign a displaced `moved` (`#lost`). Workspaces of any size hand over.
- Only `genesisPerson` runs handover. Another owner's device takes over only after 14 days past `max(HAND_OVER_FROM, genesis)` or if `genesisPerson` is no longer an owner (`mayHandOver`). Show this to users as 安全模式的升级 (pending row: 完成安全模式的升级), never "handover".
- Never wait for offline or outdated member app devices before handover. Devices below the floor receive `movedTooOld` on next contact and rejoin automatically after updating.
- Post-move, a person's existing device adds missing chain-named devices to their log. Unbound members bind via `bind` piggybacking on their next personal-lock action in one prompt (`bindsFor`), initializing a log if needed (`personal-lock.ts` `seedFor`).
- Once all named stations advertise `rootout` (`rootOutServed`), the `root` person is an ordinary member (`rules/AGENTS.md` `~root`). Their new app starts its lock anew and re-pushes pinned chains only when the reason changed (`#bringPinned`).
- Known non-goals: pre-8799 stations of another workspace keep a stale log copy after a statement. Partial build 9040-9054 handover statements contradicted by the chain stay silently ignored. Moved workspaces growing past `LOGS_BEFORE` logs with an old station misread on old cores.
- Tests: `client/core-ts/test/lock-moved-state.test.ts`, `lock-statements-made.test.ts`, `lock-handover.test.ts`, `lock-handover-model.test.ts`, `lock-left-out.test.ts`, `lock-pair-modes-faults.test.ts`, `lock-state-invariants.test.ts`.

## The vault

- A vault is always encrypted and kept by its person's own devices, with safe mode on or off. In safe mode it follows the workspace's lock in force (`client/core-ts/src/views/vault.ts` `lockOf`). Without safe mode it follows the person's own pinned lock (`personalLockOf`, genesis `""`), as each station builds it from members' own logs (`station/src/cloud/vault-lock.ts`). Turning safe mode on or off changes nothing in the vaults.
- 开启 (`vault.setup`) begins the person's own lock where none exists, with this device on it, then makes the vault and moves old plain items in (`migrate`). Nothing is written to the plain library again (`plainMode` is always false). Its items are only read to move them and delete them.
- Shared workspace vaults (`scope: "workspace"`) work both with and without safe mode: in safe mode they follow the workspace lock; without safe mode `personalLockOf` folds and verifies teammates' personal chains returned by `GET /vault/boxes` locally (never replacing this person's own pinned chain) and merges workspace roles. Workspace owners/admins who are members manage them (`canManage`).

## A person's presets and starred models

- Devices keep each workspace's records (`client/core-ts/src/presets-kept.ts` `presetRecords`, stars in `choice` `ws:<ws>:liked`) and carry updates to stations (`client/core-ts/src/views/presets.ts`) using the shared merge logic (`client/core-ts/src/preset-records.ts`, never duplicated).
- Apply local changes immediately and carry on link open, on `presets`/`stars` events, and on edit (never on a timer), sending only strictly newer records and forwarding newer station records to other reachable stations. On resumed streams, carry only `owed`/`owedStars` or first-contact `met`/`metStars` (`also` `resumed`).
- Trim kept deletions with `goneKept` (`GONE_KEPT`) so devices never send deletions a station would drop. Claim ownerless legacy deletions (`presets-kept.ts` `ownerless`) only when this device owns that preset.
- For older stations (`GET /presets/kept` returns `no route`), never PUT: use legacy endpoints, open chats by id when listed, and send `presetCopy` otherwise.
- Show own presets by default and others on press (`otherPresets`, in-memory except picked, `OTHERS_WAIT_MS` cap so slow stations do not stall the UI). Others' presets are viewable, usable, and copyable (`preset.copy`), never editable.
- How the person's agents are asked for progress (`client/core-ts/src/views/progress.ts`, `progress.set`, read in the `settings` view) is carried the same way and is one for all their workspaces: a change goes to every workspace the same account reaches.
- The board's drafts of 待派发 are the person's too and carried the same way (`client/core-ts/src/views/board-drafts.ts`, the rule `client/core-ts/src/board-drafts.ts`, the `boardDrafts` topic), no longer the prefs': what a device kept there is taken in once. A draft's files go up to the station it is to run on as they are added; another device shows them from there (`BoardDraftViews.picture`, `GET /board/files`) and, starting it, has that station copy them among its uploads (`client/core-ts/src/composer.ts` `#board`).
